## 1. Подготовка и вход в свой аккаунт

### Зачем git

Пока проект маленький, кажется, что хватит папки с файлами. Вопросы
появляются позже: «а как было неделю назад», «кто это сломал», «у меня
работает, у тебя нет», «мы вдвоём правили один файл». Git отвечает на все
четыре, потому что хранит историю снимков проекта, а не только последнюю
версию.

GitHub — сайт, куда эту историю выкладывают, чтобы она была доступна
с другого компьютера и другим людям. Git работает и без интернета; GitHub
без git не нужен.

### Выйти из чужого аккаунта

За учебным компьютером до вас сидел кто-то ещё, и VS Code помнит его
аккаунт. Если не переключиться, ваши коммиты уйдут от чужого имени.

![Значок аккаунта](img-full/002.png)

![Sign out](img-full/003.png)

### Войти в свой

![Вход в GitHub](img-full/004.png)

![Sign in](img-full/005.png)

Откроется браузер, там нужно нажать **Authorize** и разрешить доступ.

![Возврат в VS Code](img-full/006.png)

![Проверяем имя](img-full/007.png)

Внизу слева должно стоять ваше имя. Это единственная надёжная проверка —
дальше все коммиты подпишутся им.

### Представиться git

Аккаунт GitHub и подпись в коммитах — разные вещи. Git подписывает каждый
коммит именем и почтой из своих настроек, и если их не задать, коммит
просто не создастся. Один раз выполните в терминале
(<kbd>Ctrl</kbd> + <kbd>~</kbd>):

```bash
git config --global user.name "Иван Иванов"
git config --global user.email "почта, привязанная к GitHub"
```

Почта должна совпадать с той, что на GitHub, иначе коммиты не свяжутся
с вашим профилем.

### Панель, в которой всё происходит

![Панель Source Control](img/01-source-control.png)

Открывается сочетанием <kbd>Cmd/Ctrl</kbd> + <kbd>Shift</kbd> + <kbd>G</kbd>.
Дальше почти вся работа будет здесь.

## 2. Первый репозиторий

Есть два начала: забрать готовый проект или начать свой.

![Пустое окно VS Code](img-full/008.png)

### Склонировать чужой проект

![Клонирование](img/02-clone.png)

**Clone Repository** попросит адрес — можно вставить ссылку вида
`https://github.com/user/repo.git`. Но если GitHub уже подключён, проще
выбрать **Clone from GitHub**: VS Code сам покажет список ваших
репозиториев.

![Список репозиториев](img-full/010.png)

![Выбор репозитория](img-full/011.png)

Дальше выбираете папку, куда положить копию. Скачаются не только файлы,
но и вся история проекта.

![Клонирование завершено](img-full/012.png)

> В терминале: `git clone https://github.com/user/repo.git`

### Начать свой

Открываете пустую папку (**File → Open Folder**) и заходите в Source Control:

![Инициализация репозитория](img/03-init.png)

**Initialize Repository** создаёт внутри папки скрытый каталог `.git` —
с этого момента git следит за изменениями. Внешне ничего не меняется,
файлы остаются на месте.

**Publish to GitHub** делает то же самое и сразу заводит репозиторий
на сайте.

> В терминале: `git init`

## 3. Изменения и коммиты

Создайте пару файлов — и панель оживёт.

![Создали файлы](img-full/014.png)

![Git увидел изменения](img-full/015.png)

![Панель Source Control](img/04-source-control.png)

Каждый файл помечен буквой:

| Буква | Что значит |
|---|---|
| `U` | untracked — новый файл, git его раньше не видел |
| `M` | modified — файл был и изменился |
| `D` | deleted — файл удалён |

### Два шага вместо одного

Git не сохраняет всё подряд: сначала вы **отбираете**, что войдёт в снимок,
и только потом делаете снимок. Так можно закоммитить одну часть работы,
а вторую оставить на потом.

![Добавление файла в коммит](img/05-stage.png)

Отобранные файлы переезжают в раздел **Staged Changes** — это корзина
будущего коммита. Клик по имени файла открывает сравнение: слева было,
справа стало.

![Просмотр файла](img-full/018.png)

> В терминале: `git add hello.py` — один файл, `git add .` — все сразу

### Коммит

Пишете сообщение и нажимаете **Commit**. Сообщение — не формальность:
через месяц по списку коммитов вы будете искать, где что сломалось.

```
плохо                     хорошо
fix                       hw-01: разбор знакомого сервиса
update                    lesson_07: максимум за один проход
изменения                 fix: пустой список больше не роняет /orders
```

![Коммит создан](img-full/020.png)

> В терминале: `git commit -m "hw-01: разбор знакомого сервиса"`

### Если коммит не создаётся

![Ошибка при коммите](img/15-commit-error.png)

Git не знает, кто вы. Вернитесь к разделу 1 и выполните две команды
`git config` — после этого коммит пройдёт, переделывать ничего не нужно.

## 4. Публикация на GitHub

После первого коммита на месте кнопки Commit появляется **Publish Branch**.

![Publish Branch](img/06-publish.png)

Если репозитория на сайте ещё нет, VS Code спросит имя и видимость:

![Выбор видимости](img/16-publish-choice.png)

**Private** — репозиторий видите только вы и те, кому дадите доступ.
**Public** — виден всем. Для учебных работ обычно берут private, а ссылку
выдают преподавателю.

### Если публикация не прошла

![Ошибка публикации](img-full/023.png)

![Команда в терминале](img-full/024.png)

![Повторный вход](img-full/025.png)

Чаще всего дело в незавершённом входе в GitHub: выполняете подсказанную
команду, повторяете **Publish Branch** и подтверждаете вход в браузере.

### Результат

![Репозиторий на GitHub](img-full/026.png)

![История коммитов](img-full/027.png)

На сайте появился репозиторий с вашими файлами и историей.

> В терминале это три команды: `git remote add origin <адрес>`,
> `git branch -M main`, `git push -u origin main`

**Коммиты после публикации удалить нельзя** — можно только сделать новый,
который отменяет изменения. История это дорога в одну сторону.

### Как читать граф

![Граф коммитов](img/07-graph.png)

Читается снизу вверх: внизу самые старые коммиты, вверху свежие. Цветные
метки показывают, где сейчас **находится** каждая ветка:

- `main` — ваша основная ветка на компьютере;
- `origin/main` и `origin/HEAD` — та же ветка, но на GitHub. Если метки
  разъехались, значит у вас есть коммиты, которых нет на сайте, или наоборот;
- короткий код вида `a28c361` — адрес коммита, по нему на него ссылаются.

## 6. Ветки внутри проекта

Ветка — отдельная линия работы. Вы копируете текущее состояние проекта,
меняете что хотите, и основная версия не страдает, пока вы сами не сольёте
изменения. Не получилось — ветку просто удаляют.

Правило: **в `main` лежит рабочая версия**, эксперименты и новые функции
живут в отдельных ветках.

### Создать и переключиться

![Имя ветки в статус-баре](img-full/039.png)

![Меню ветки](img-full/040.png)

![Меню веток](img/08-branch-menu.png)

![Имя новой ветки](img-full/041.png)

![Список веток](img-full/043.png)

После создания имя в статус-баре меняется — вы уже в новой ветке. Всё, что
вы теперь коммитите, попадает в неё.

> В терминале: `git switch -c имя-ветки`, обратно — `git switch main`

### Убедитесь, что ветки правда независимы

Создайте на новой ветке пару файлов и закоммитьте:

![Файлы на новой ветке](img-full/044.png)

![Коммит на ветке](img-full/046.png)

![Файлов нет в main](img-full/045.png)

![Файлы на месте](img-full/047.png)

![Проверяем ветку](img-full/048.png)

Пока это не увидишь своими глазами, ветки кажутся магией.

### Слить ветку в main

![Граф: ветка ушла вперёд](img-full/049.png)

Порядок такой: **сначала переходим в ту ветку, куда вливаем**, и только
потом запускаем слияние.

![Меню слияния](img/09-merge-menu.png)

![Выбор ветки](img-full/052.png)

![Слияние идёт](img-full/053.png)

![Файлы появились в main](img-full/054.png)

После слияния в `main` появляются и файлы, и все коммиты из ветки. Остаётся

![Отправка на GitHub](img-full/055.png)

> В терминале: `git switch main` → `git merge имя-ветки`

## 8. Коммиты с помощью ИИ

В VS Code рядом с полем сообщения есть значок с искрами: он читает
подготовленные изменения и предлагает текст коммита.

![Значок с искрами](img-full/088.png)

![Изменённый файл](img-full/089.png)

![Staged Changes](img-full/090.png)

![Предложенный текст](img-full/091.png)

Пользоваться удобно, но правило то же, что и с кодом: **прочитайте, что
он написал**. Модель видит только изменения и не знает, зачем вы их делали, —
поэтому «обновил файл» она напишет там, где нужно «fix: пустой список
больше не роняет /orders».

### Сообщения на русском

![Палитра команд](img-full/092.png)

![Настройки JSON](img-full/093.png)

Открываете настройки (<kbd>Cmd/Ctrl</kbd> + <kbd>Shift</kbd> + <kbd>P</kbd> →
*Open User Settings (JSON)*) и добавляете:

```json
"github.copilot.chat.commitMessageGeneration.instructions": [
  {
    "text": "Пиши сообщения коммитов на русском языке. Если используешь Conventional Commits, оставляй тип на английском: feat, fix, docs, refactor, test, chore."
  }
]
```

![Результат вставки](img-full/094.png)

![Файл настроек](img-full/095.png)

Если в файле уже что-то есть, не забудьте запятую перед вставкой. Набор
настроек у вас может отличаться от примера — это нормально.

## 9. Конфликты при слиянии

Конфликт возникает, когда две ветки изменили **одну и ту же строку**
по-разному. Git не угадывает, чья версия правильная, и останавливается,
чтобы решили вы. Никакой поломки при этом не происходит: файлы целы,
слияние просто поставлено на паузу.

### Как прийти к конфликту специально

Создаём `profile.txt`:

```
name: Student
role: developer
status: active
```

![Создали profile.txt](img-full/096.png)

И `README.md` рядом:

![Создали README](img-full/097.png)

Фиксируем стартовую версию коммитом:

![Стартовый коммит](img-full/098.png)

Создаём ветку и меняем в ней роль на `backend developer`:

![Новая ветка](img-full/099.png)

![Меняем строку](img-full/100.png)

![Коммит в ветке](img-full/101.png)

Возвращаемся в `main` и меняем ту же строку иначе — на `frontend developer`:

![Меняем в main](img-full/102.png)

![Коммит в main](img-full/103.png)

Теперь сливаем ветку:

![Запускаем слияние](img-full/104.png)

![Git сообщает о конфликте](img-full/105.png)

### Что видно в файле

![Конфликт в файле](img/11-conflict.png)

```
<<<<<<< HEAD
role: frontend developer      ← ваша версия, из ветки, где вы находитесь
=======
role: backend developer       ← входящая, из ветки, которую вливаете
>>>>>>> conflict-01-role-backend
```

Над конфликтом VS Code показывает четыре кнопки:

![Кнопки решения](img-full/107.png)

| Кнопка | Что делает |
|---|---|
| Accept Current Change | оставить свою версию |
| Accept Incoming Change | оставить входящую |
| Accept Both Changes | оставить обе строки |
| Compare Changes | открыть сравнение, если непонятно, что поменялось |

![Обе строки оставлены](img-full/108.png)

![Compare Changes](img-full/109.png)

Выбираете вариант, проверяете, что в файле не осталось `<<<<<<<`
и `>>>>>>>`, сохраняете — и нажимаете **Continue**. Слияние завершится
обычным коммитом.

### Если ветки разошлись

Вы поменяли файл у себя, а кто-то другой — тот же файл на GitHub.

![Локальное изменение](img-full/117.png)

![Чужое изменение на сайте](img-full/118.png)

![Sync Changes](img/12-sync.png)

Стрелки на кнопке говорят всё: `1↓` — один чужой коммит нужно скачать,
`1↑` — один свой отправить. Попытка сделать это одним движением закончится
ошибкой:

![Ошибка синхронизации](img-full/120.png)

Порядок разбора:

1. Сначала **забрать** чужие изменения (`Pull`), а не отправлять свои.

## 11. Служебные файлы

### .gitignore

Список того, что git не должен отслеживать. Нужен, чтобы в репозиторий
не попадали временные файлы, виртуальные окружения, кэш и — главное —
**пароли и токены**.

```gitignore
# Python
.venv/
__pycache__/
*.pyc
.env

# системное и редакторы
.DS_Store
.vscode/
.idea/
```

Важно: если файл **уже** попал в git, добавить его в `.gitignore` мало —
git продолжит его отслеживать. Нужно убрать его из индекса:

```bash
git rm --cached .env
```

### .gitkeep

Git хранит файлы, а не папки: пустую папку он просто не заметит. Если
структура важна (например, нужна папка `logs/`), внутрь кладут пустой файл
`.gitkeep`. Это не команда git, а договорённость между разработчиками —
имя может быть любым, просто это прижилось.

### README.md

Файл, который GitHub показывает на главной странице репозитория. Обычно
в нём: название проекта, короткое описание, как запустить, что умеет
и кто автор. Пишется на Markdown — том же формате, что и этот документ.

```markdown
# Название проекта

Краткое описание.

## Запуск

    python main.py
```

| Файл | Зачем |
|---|---|
| `.gitignore` | не пускает в репозиторий мусор и секреты |
| `.gitkeep` | сохраняет пустую папку |
| `README.md` | описывает проект на GitHub |

## 12. Шпаргалка

| В VS Code | В терминале | Что делает |
|---|---|---|
| Clone Repository | `git clone <адрес>` | забрать проект с историей |
| Initialize Repository | `git init` | начать следить за папкой |
| `+` у файла | `git add файл` | отобрать файл в коммит |
| `+` у строки Changes | `git add .` | отобрать все изменения |
| Commit | `git commit -m "..."` | сохранить снимок в историю |
| Publish Branch | `git push -u origin main` | отправить ветку на GitHub |
| Sync Changes | `git pull` + `git push` | обменяться изменениями |
| Клик по имени ветки → Create new branch | `git switch -c имя` | создать ветку и перейти в неё |
| Клик по имени ветки → выбрать другую | `git switch main` | переключиться |
| Branch → Merge | `git merge имя` | влить ветку в текущую |
| Branch → Delete Branch | `git branch -d имя` | удалить отработавшую ветку |
| Pull | `git pull` | забрать чужие изменения |
| Fetch | `git fetch` | посмотреть, что нового, не трогая файлы |
| Git Graph | `git log --oneline --graph` | история и ветки |
