## 1. Заказы за сутки, `n ≤ 200 000`

Есть ли среди номеров хотя бы два одинаковых?

- **Проходит:** O(n) по времени и O(n) по памяти
- **Решение:** Пройти по списку номеров один раз, сохраняя посещённые номера в хэш-таблицу set. Если номер уже есть в множестве - дубликат найден
- **Что мешало проще:** Обычный перебор двумя вложенными циклами имеет сложность O(n^2), что слишком медленно для таких ограничений
- **Почему это верно (с числом):** При n = 200 000 наивный перебор O(n^2) занял бы (200 000)^2 / 2 = 2 * 10^10 операций, что превышает лимит в 10^7 операций в секунду в 2000 раз. Алгоритм с хэш-таблицей совершит всего около 200 000 операций, что укладывается в 0.02 секунды

## 2. Цены на складе, `n ≤ 100 000`

Найти три самые дешёвые позиции.

- **Проходит:** O(n) по времени и O(1) по дополнительной памяти
- **Решение:** Пройти по массиву один раз и в один проход поддерживать три минимальных значения в отдельных переменных
- **Что мешало проще:** Полная сортировка массива O(n log n) работает дольше и требует лишних действий, хотя для n = 100 000 она бы тоже уложилась в лимит
- **Почему это верно (с числом):** При n = 100 000 поиск трёх минимумов за один проход займет ровно 100 000 итераций. Это ничтожно мало по сравнению с лимитом 10^7 операций, всего 1% от секундного лимита

## 3. Архив чеков `n ≤ 10⁷`, запросов `q ≤ 10⁵`

Отсортирован. По каждому запросу сказать, есть ли такой чек.

- **Проходит:** O(q log n) по времени
- **Решение:** Для каждого из q запросов запустить бинарный поиск по уже отсортированному массиву чеков
- **Что мешало проще:** Простой линейный поиск O(n) для каждого запроса превратил бы общую сложность в O(q * n), что абсолютно неприемлемо
- **Почему это верно (с числом):** Линейный поиск потребовал бы q * n = 10^5 * 10^7 = 10^12 операций. Бинарный поиск для одного запроса делает log₂(10^7) ≈ 24 операции. Суммарно для всех запросов выйдет 10^5 * 24 = 2.4 * 10^6 операций, что значительно меньше порога в 10^7 операций

## 4. Координаты курьеров, `n ≤ 3 000`

Найти двух ближайших друг к другу.

- **Проходит:** O(n^2) по времени
- **Решение:** Полный перебор всех пар курьеров через два вложенных цикла для вычисления расстояния между ними
- **Что мешало проще:** Существуют более сложные алгоритмы (например, разделяй и властвуй за O(n log n)), но их написание избыточно, так как n достаточно мало
- **Почему это верно (с числом):** Для n = 3 000 количество пар в переборе составляет n * (n - 1) / 2 = 3000 * 2999 / 2 ≈ 4.5 * 10^6 операций. Это число меньше 10^7, поэтому стандартный перебор гарантированно уложится в одну секунду

## 5. Одно число `k ≤ 10⁹`

Сколько раз его можно разделить пополам до единицы?

- **Проходит:** O(log k) по времени
- **Решение:** Обычный цикл while k > 1: k //= 2 со счётчиком шагов или вычисление двоичного логарифма
- **Что мешало проще:** Число k очень большое, но деление пополам уменьшает его экспоненциально быстро, поэтому делать что-то сложнее нет смысла
- **Почему это верно (с числом):** Даже для максимального значения k = 10^9 цикл выполнится всего log2(10^9) ≈ 30 раз. 30 операций — это мгновенное выполнение, которое бесконечно далеко от лимита в 10^7 операций

## 6. Две накладные, `n ≤ 10⁵` и `m ≤ 10⁵`

Обе отсортированы. Собрать из них один отсортированный список.

- **Проходит:** O(n + m) по времени
- **Решение:** Использовать два указателя. Сравнивать текущие элементы в обеих накладных и продвигать тот указатель, где элемент меньше, поочередно добавляя их в новый список
- **Что мешало проще:** Слияние списков через стандартный .extend() и последующую общую сортировку sort() заняло бы O((n+m) log(n+m)), что проигрывает линейному слиянию
- **Почему это верно (с числом):** Алгоритм двух указателей сделает ровно n + m шагов. При n = 10^5 и m = 10^5 это составит 10^5 + 10^5 = 2 * 10^5 операций, что в 50 раз меньше допустимого порога в 10^7 операций в секунду
